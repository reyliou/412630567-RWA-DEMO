## 二、適用性說明（必讀）

五個情境中有**兩項在本系統的架構下沒有字面上的對應機制**。若照字面撰寫，等於測一個不存在的東西。經逐一確認程式碼後，改測最接近的等價風險，並在測試名稱中明白標示。

### 情境二「重複事件」—— 系統沒有事件監聽器

全專案**沒有任何鏈上事件訂閱**：不存在 `contract.on`、`provider.on`、`addListener` 或 WebSocket listener。唯一消費 `Transfer` 事件的地方是 `reconcile()` 內的一處 `queryFilter`，屬於「每次呼叫時全量重建鏈上餘額」的比對式讀取，不是持續監聽。

因此「同一事件被監聽兩次而重複入帳」在本系統中不成立。等價風險是**對帳被重複執行時會不會重複入帳**，本文件測的是這個。

### 情境四「區塊重組」—— 程式沒有 reorg 處理

程式中所有 `.wait()` 皆未帶確認數參數，等同**預設 1 個確認**，也就是假設一個區塊即最終性。沒有任何針對 reorg 的重新驗證或回捲邏輯。

等價風險是**已入帳的交易若在鏈上被 reorg 掉，系統偵測不偵測得到**。唯一的安全網是 `reconcile()`，本文件測的是這個。

> 若報告需寫「已涵蓋重複事件／區塊重組」，請連同上述但書一併說明，否則與實際實作不符。

## 四、各情境詳細

### (a) 情境一：服務重啟後的 pending 交易狀態

**注入方式**：讓 `commitTransaction()` 拋出模擬的程序中斷錯誤，觀察交易狀態與鏈上呼叫次數。

| 測試情境 | 預期結果 | 實際結果 | 結果 |
|---|---|---|---|
| 寫入途中程序被砍（commit 失敗） | 整筆 rollback、釋放連線，不得留下半完成狀態 | `rollbackTransaction` 與 `release` 各執行 1 次 | ✅ |
| 🔴 鏈上轉帳成功但 DB commit 失敗，重啟後重新結算 | （現況觀察）鏈上動作會被重跑 | 實測 `executeOnChainBuy` 被呼叫 **2 次**，使用者僅入帳 1 次 | ⚠️ 已知風險 |

**發現**：鏈上呼叫位於 DB commit **之前**（`transactions.service.ts` 的註解即寫著 `On-chain transfer (before DB commit)`），且重新結算前未檢查該筆是否已有 `tx_hash`。程序若在「鏈上已成功、DB 尚未 commit」的空窗被中斷，重啟後必然重跑鏈上轉帳，多付出的代幣無法自動追回。

現況安全網僅有 `reconcile()`，屬事後偵測而非事前防止。

**建議修法**：結算前先以 `tx_hash` 或獨立的「鏈上已送出」旗標做冪等檢查。

---

### (b) 情境二：重複事件（等價風險 — 對帳重複執行）

**注入方式**：以固定的 `Transfer` 事件集合連續執行兩次 `reconcile()`，比對兩次結果。

| 測試情境 | 預期結果 | 實際結果 | 結果 |
|---|---|---|---|
| 連續執行兩次對帳 | 同一筆不一致不得被累計成兩筆 | 兩次的不一致筆數與檢查建案數完全相同 | ✅ |
| 鏈上轉帳已有對應交易紀錄 | 不得再判定為未追蹤轉帳（避免重複補建） | `UNTRACKED_TRANSFER` 為 0 筆 | ✅ |

**結論**：對帳為無狀態的全量比對，天生冪等，重跑不會重複入帳。

---

### (c) 情境三：Nonce 衝突

**注入方式**：讓合約的 `transfer()` 拋出帶 `code = 'NONCE_EXPIRED'` 的錯誤，觀察錯誤傳遞、快取處理與資料庫狀態。

| 測試情境 | 預期結果 | 實際結果 | 結果 |
|---|---|---|---|
| 鏈上轉帳遇 `NONCE_EXPIRED` | 錯誤如實往外拋，不得吞掉造成成功假象 | 正確拋出 | ✅ |
| nonce 脫節後的快取處理 | 應清除 `NonceManager` 快取，讓下一筆重新向節點取號 | `reset()` 被呼叫 1 次 | ✅ |
| 非 nonce 類的鏈上失敗（例：ERC-3643 合規擋下） | **不得**觸發 reset | `reset()` 未被呼叫 | ✅ |
| nonce 衝突後的資料庫狀態 | 標記 `CHAIN_FAILED`，且不得寫入假的 `tx_hash` | 狀態正確，`tx_hash` 維持未設定 | ✅ |

**已修正**：admin 錢包以 `ethers.NonceManager` 包裝，所有鏈上寫入共用同一把私鑰。先前程式中**沒有任何 `NonceManager.reset()` 的呼叫**，一旦送出失敗導致本地 nonce 計數與鏈上實際值脫節，後續每一筆都會沿用錯誤的 nonce 而連續失敗，直到服務重啟。

現已於 `executeOnChainBuy()` / `executeOnChainSell()` 的失敗路徑加入 `resetNonceIfDesynced()`：

```ts
private resetNonceIfDesynced(e: any) {
  const code = String(e?.code ?? '');
  if (code !== 'NONCE_EXPIRED' && code !== 'REPLACEMENT_UNDERPRICED') return;
  (this.adminWallet as any)?.reset?.();
  this.logger.warn(`⚠️ 偵測到 nonce 脫節 (${code})，已清除 NonceManager 快取，下一筆將重新向節點取號`);
}
```

**刻意只在兩種錯誤碼時才 reset** —— 其他失敗（例如合規檢查擋下轉帳）並不會讓 nonce 脫節，若一律 reset，反而可能在有其他交易在途時造成重號。上表第 3 筆即為此邊界撰寫。

---

### (d) 情境四：區塊重組（等價風險 — 對帳能否偵測）

**注入方式**：模擬 reorg 後鏈上查無任何 `Transfer` 事件，但資料庫仍記著使用者持有 500 枚，觀察對帳是否偵測得到。

| 測試情境 | 預期結果 | 實際結果 | 結果 |
|---|---|---|---|
| 已入帳的轉帳在鏈上被 reorg 掉 | 對帳須偵測為餘額不一致 | 偵測到 `BALANCE_MISMATCH`，鏈上 0 / 資料庫 500 | ✅ |
| 偵測到不一致時的稽核紀錄 | 應寫入 `system_alerts` 而非靜默 | `logAlert` 確實被呼叫 | ✅ |

**觀察**：所有 `.wait()` 均為預設 1 個確認數，等同假設 1 個區塊即最終性。本專題在 Hardhat 本機網路上不會發生 reorg，但若上正式鏈需提高確認數。

---

### (e) 情境五：成交通知寄送失敗

**注入方式**：讓通知的寫入拋出模擬故障，觀察交易是否 commit、鏈上轉帳是否被連帶回滾。

| 測試情境 | 預期結果 | 實際結果 | 結果 |
|---|---|---|---|
| 通知寫入失敗時的交易結果 | 交易須照常 commit，通知失敗只記錄告警 | `commitTransaction` 執行 1 次、未 rollback、鏈上轉帳保留 | ✅ |
| 通知的寫入時機與連線 | 須在 commit 之後、且不得再使用交易的 `queryRunner` | 交易範圍內查無通知寫入，改由獨立 repository 寫入 | ✅ |

**已修正**：先前成交通知使用與交易**相同的 `queryRunner`**（`qr.manager.save(UserNotification, ...)`）且位於 commit 之前，因此純通知層的故障會連帶讓一筆**已經上鏈**的交易被回滾 —— 代幣在使用者鏈上錢包裡，平台帳上卻沒有這筆交易。

現已將通知寫入移到 `commitTransaction()` 之後，改以獨立的 `notifRepo` 寫入並自帶 try/catch，失敗僅記錄 ERROR：

```ts
await qr.commitTransaction();

try {
  await this.notifRepo.save({ user_id: userId, title: ..., message: msg, is_read: false } as any);
} catch (notifyErr: any) {
  this.logger.error(`成交通知寫入失敗（交易已完成，不受影響）: ${notifyErr.message}`);
}
```

通知屬於可補送的周邊功能，不應具備否決已完成鏈上轉帳的能力。代價是通知本身在極端情況下可能遺失，但相較於回滾一筆已上鏈的交易，這是明確較小的損失。
