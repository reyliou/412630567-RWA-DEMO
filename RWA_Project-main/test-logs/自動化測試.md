| 測試情境 | 預期結果 | 實際結果 | 結果 |
|---|---|---|---|
| 不同 idempotency_key 併發下單 | 兩筆都應成交，各自寫入 | 兩筆皆成功 | ✅ |
| 🔴 **相同 idempotency_key 併發下單兩次** | （現況觀察）可能兩筆都通過檢查而重複寫入 | 實測：2 個併發請求中，mock 資料庫寫入了 2 次相同的 idempotency_key（侷限見下方說明） | ⚠️ 已知風險 |
| 資料庫 UNIQUE 約束擋下重複的 idempotency_key | 應轉為明確的「偵測到重複交易」訊息並回 `400`，而非未處理的資料庫例外（`500`） | 正確攔截並回傳預期訊息 | ✅ |
| 其他唯一約束衝突（同為 `23505`，但語意不同） | 不應被誤報成「重複交易」，訊息須指出實際違反的約束（例：`UQ_user_holdings_user_property`） | 正確回報實際約束名稱，未被掩蓋成重複交易 | ✅ |
| AMM 讀取建案資料時的鎖定策略 | 應帶入 `lock: { mode: 'pessimistic_write' }`，使同一建案的交易序列化 | 確實帶入 | ✅ |
| 鎖的取得時機 | 排他鎖必須在 `startTransaction()` 之後才取得，否則不具效力 | 建案查詢排在冪等性查詢之後，位於交易範圍內 | ✅ |

**Log 摘要**：
```
[併發測試 log] 2 個併發請求 → 成功 2/2 筆，資料庫實際寫入相同 idempotency_key 共 2 次
```

**發現與說明**：市價單（`runTrade`）的重複交易檢查（先 `findOne` 查詢、再寫入）發生在資料庫交易開始（`startTransaction`）之前，屬於 TOCTOU（Time-of-check to time-of-use）競態條件。高併發下同一個 idempotency_key 有機率繞過應用層的重複攔截。

**測試方法的侷限（重要）**：本測試以共用陣列 mock 資料庫寫入，因此**觀察不到資料庫層級的 UNIQUE 約束**。log 顯示的「寫入 2 次」是 mock 環境的結果，不代表正式環境行為 —— `AppTransaction` entity 上已宣告 `@Column({ type: 'uuid', nullable: true, unique: true })`，真實 PostgreSQL 會在第二筆 INSERT 時直接以 `23505` 拒絕。換言之，**資料完整性本身沒有破口**。

**實際仍存在的缺口**：`23505` 目前只在**限價單**路徑被攔截並轉為 `400 BadRequestException`（`transactions.service.ts`），**市價單路徑沒有對應的 catch**。因此真實環境下併發送出重複的市價單，第二筆會以未處理的資料庫例外形式冒出，回應變成 `500` 而非語意明確的「偵測到重複交易」`400`。這是錯誤處理的缺口，不是資料正確性的缺口。

**修正結果**：已在 `runTrade` 的例外處理補上與限價單相同的 `err.code === '23505'` 判斷，統一回傳「偵測到重複交易，已為您安全攔截」並轉為 `400`。上表第 3 筆測試即針對此修正撰寫 —— 它直接注入一個 `code = '23505'` 的例外，模擬 TOCTOU 實際發生時資料庫擋下後到請求的情境；若移除該判斷，拋出的會是 PostgreSQL 的原始訊息而非預期文字，測試會立即失敗。

**修正的副作用與再修正**：`23505` 並非只有冪等性約束會觸發 —— `user_holdings` 的 `(user_id, property_id, holder_type)` 約束衝突同樣是 `23505`，但語意完全不同。上述修正若一律回報「重複交易」，會把真正的結構問題掩蓋掉（實際遇過限價單每 5 秒重試一次、log 只寫「重複交易」而查不出原因的情況）。現已改為依 `constraint` 名稱分辨：僅冪等性約束回報重複交易，其餘照實指出違反的約束。上表第 4 筆即針對此再修正撰寫。

**後續補強（本文件撰寫後追加）**：AMM 的「讀取流通量 → 計算價格與滑價 → 寫入」區段原本沒有任何鎖定，在預設的 READ COMMITTED 隔離等級下，兩筆同時進入的交易會讀到相同的流通量、算出相同價格，各自通過滑價檢查後雙雙成交，等同第二筆以過期價格成交（lost update）。現已於資料庫交易起始處對該建案列取得 `pessimistic_write` 排他鎖，使同一建案的交易彼此序列化。該鎖為交易的第一個語句且永遠只鎖單一列，不會形成死鎖環。上表後兩筆測試即針對此修正撰寫。

**鎖定測試的效力範圍（誠實說明）**：上表第 5、6 筆驗證的是「服務層確實向 TypeORM 要求了排他鎖，且要求的時機落在資料庫交易範圍內」，屬於程式碼契約層級的驗證 —— 若日後有人不慎移除 `lock` 參數或把查詢移到 `startTransaction()` 之前，測試會立即失敗。至於排他鎖在真實併發下的實際阻塞行為，由 PostgreSQL 本身保證，需連線真實資料庫並以兩條獨立連線同時下單才能觀察，不在本測試涵蓋範圍。

## 七、效能測試 (Performance Test)

**環境**：本機 Node.js 服務（`npm run start:dev`）連線至雲端 Supabase（`aws-1-ap-southeast-2.pooler.supabase.com:6543`，PgBouncer Transaction Pooling 模式）
**工具**：autocannon（20 個併發連線，持續 20 秒）
**測試對象**：`GET /api/properties/:id/kline`、`GET /api/orderbook/:id`
**樣本**：2 種限流情境 × 2 支 API = 4 組壓測。情境 A（保留限流）K 線 79,000 筆、掛單簿 88,000 筆請求；情境 B（解除限流）K 線 645 筆、掛單簿 323 筆請求
**評估方式**：效能測試不以「通過／失敗」計分，而以延遲、吞吐量、錯誤數三項指標呈現。以下數據取自附錄三的 autocannon 原始輸出

### 7.1 情境 A：保留 Throttler 限流保護（預設 `100 次/60 秒`，全站套用）

| 項目 | K 線查詢 | 掛單簿查詢 |
|---|---|---|
| 平均延遲 | **4071.69 ms** | 3.95 ms |
| p50 延遲 | 2258 ms | 2 ms |
| p99 延遲 | 12,617 ms | 4 ms |
| 最大延遲 | 13,105 ms | 3221 ms |
| 平均吞吐量 | 3155.15 req/s | 4400.7 req/s |
| 總請求數 | 79,000 筆 / 20.05s | 88,000 筆 / 20.08s |
| 2xx 成功 | 200 筆 | 100 筆 |
| 非 2xx（429 限流拒絕） | 62,900 筆 | 87,901 筆 |
| **連線層錯誤 / 逾時** | **16,000 / 0** | **0 / 0** |

**結論（兩支端點的對照才是重點）**：

Throttler 本身運作正常——`limit = 100 次/60 秒`，20 秒的壓測期間分別只有 200 筆與 100 筆請求進到業務邏輯，其餘全數以 429 擋下，符合設定。

但兩支端點的表現差距極大：

- **掛單簿**：平均延遲 3.95 ms、**零錯誤**。限流在請求觸及業務邏輯前就攔下，系統幾乎不耗資源。
- **K 線**：平均延遲 **4.07 秒**、p99 **12.6 秒**，79,000 筆請求中有 **16,000 筆（約 20%）在連線層失敗**。

差別在於運算成本。K 線端點需撈取最多 3,000 筆交易再於應用層做 OHLC 聚合，即使多數請求被限流擋下，少數穿透的請求仍足以讓連線池與事件迴圈壅塞，導致後續連線被拒。掛單簿的 SQL 由資料庫直接彙總（`GROUP BY` + `LIMIT 5`），負載輕得多。

**這個對照說明限流不能取代端點本身的效能優化**：限流保護的是「業務邏輯不被打爆」，但無法阻止重運算端點在高併發下於連線層崩解。此結果直接支持 7.4 提出的快取層與聚合下放建議。

### 7.2 情境 B：暫時解除限流（`limit` 臨時調整為 100000，測試後已還原為 100）

拿掉限流後，所有請求都會實際打到資料庫，因此這組數據反映的是**系統真正的處理能力上限**。

| 項目 | K 線查詢 | 掛單簿查詢 |
|---|---|---|
| 平均延遲 | 632.88 ms | 1277.33 ms |
| p50 延遲 | 577 ms | 1157 ms |
| p99 延遲 | 2370 ms | 2998 ms |
| 最大延遲 | 2581 ms | 3211 ms |
| 平均吞吐量 | 31.25 req/s | 15.15 req/s |
| 總請求數 | 645 筆 / 20.14s | 323 筆 / 20.16s |
| 錯誤 / 逾時 | 0 / 0 | 0 / 0 |

**結論**：吞吐量從限流時的每秒數千次驟降到 **15～31 req/s**，落差三個數量級——證實限流情境下的高吞吐量幾乎全部來自 429 的快速拒絕，而非系統真的處理得動。此處無任何錯誤，代表在請求速率降下來之後系統本身是穩定的，瓶頸單純是每筆請求的延遲過高。

值得注意的是 **K 線的平均延遲（632.88 ms）與純 TCP 連線耗時（約 550 ms，見 7.3 步驟 3）幾乎相同**——換言之，約 87% 的延遲來自建立到雪梨機房的網路連線，真正花在查詢與運算上的時間不到 100 ms。這也解釋了為何情境 A 中 K 線會出現連線層錯誤：每筆請求都被迫重新承擔約半秒的連線成本。

### 7.3 根因排查過程（排除法）

| 步驟 | 方法 | 目的 | 結果 |
|---|---|---|---|
| 1 | `EXPLAIN ANALYZE` 檢視 SQL 執行計畫 | 排除資料庫缺乏索引 | 確認使用 `idx_transactions_property_time` 索引，查詢僅需 0.3 ms，排除索引問題 |
| 2 | 連續 5 次序列（非併發）單一請求 | 排除 Supabase 冷啟動 / 喚醒延遲 | 第 1 次 1.03s，第 2~5 次穩定在 0.6~0.9s，排除單純冷啟動假設，確立穩定基線延遲 |
| 3 | 純 TCP Socket 連續 5 次直連資料庫主機 | 隔離「應用層計算」與「底層網路連線」兩種可能性 | 第 1 次 2.1s，第 2~5 次穩定在 530~560ms，證實純網路層開銷即佔基線延遲的主要部分 |
| 4 | 檢查 `.env` 的 `DATABASE_URL` | 確認連線模式 | 確認為 `:6543` + `pgbouncer=true`（PgBouncer Transaction Pooling），連線在每筆交易結束後即被回收，無法有效重用 TCP/TLS 連線 |

**最終判斷**：延遲瓶頸主要來自（a）本機至雪梨機房的跨國網路延遲、（b）PgBouncer Transaction Pooling 模式下連線無法有效重用、（c）TypeORM 未設定連線池 `max`（預設 10），在 20 個併發請求下造成排隊等待，三者疊加導致 p99 延遲達到 2.4～3.0 秒。

其中（a）有明確的量化佐證：步驟 3 的純 TCP 連線測試顯示穩定狀態下單次連線即需 530～560 ms，而情境 B 的 K 線平均延遲為 632.88 ms——**網路連線本身就佔了約 87%**。

> **資料完整性說明**：步驟 1 的 `EXPLAIN ANALYZE` 於執行時因命令列引號跳脫問題連續失敗（PowerShell 對巢狀引號的處理），未能保留原始查詢計畫輸出，該列結論係依當時終端機畫面記錄。步驟 2、3 的原始輸出完整保留於附錄三。

**待延伸驗證方向**（受限於時間未完成）：重新取得 `EXPLAIN ANALYZE` 的完整輸出、ISP 路由本身的細節成因、實際切換連線模式（Session Pooling / 直連）後的延遲對照。

### 7.4 優化建議

1. **短期**：導入 Redis 快取層（TTL 3-5 秒），攔截高頻重複的唯讀查詢，繞過網路與連線池瓶頸；搭配快取後再考慮放寬唯讀查詢的限流額度。
2. **長期**：將 OHLC 聚合邏輯下放至資料庫端（`GROUP BY` / Materialized View），並評估將應用伺服器部署到與資料庫相同區域（ap-southeast-2）以從架構層面消除跨國延遲。
3. **限流策略**：導入 `@nestjs/throttler` 的 Multiple Throttlers，唯讀查詢與寫入類 API 分開設定額度，避免同教室多人共用網路時誤觸全站限流。

### 7.5 執行方式

```bash
cd RWA_Project-main/rwa-backend
npm run start:dev            # 另開終端機啟動服務
node test/perf/autocannon-test.js
```

7.1、7.2 兩張表格的所有數值均取自 **附錄三** 的 autocannon 原始輸出，可逐項對照。

### 8.3 節點失憶的自動重建判斷

**測試對象**：`autoRecoverNodeState()` —— 每 30 秒執行一次的排程，偵測到「節點失憶」（雲端休眠重啟導致鏈上狀態被清空）就自動呼叫 `setupBlockchain()` 重新部署整套 T-REX 並重新鑄造。

**為什麼這條路徑必須有測試**：這是整個服務裡**後果最重的自動化路徑**。判斷失準的代價不是回傳錯誤訊息，而是在無人介入的情況下重新部署合約、鏈上餘額全部歸零。判斷的核心是 `isConfigStale()`，它以 `provider.getCode(irAddr)` 是否回傳 `0x` 來認定合約是否還存在，因此三種可能結果都必須各有一筆測試守住。

**測試方式**：讓服務進入「節點可達、且資料庫記得曾經部署過」的狀態，再注入 `getCode` 的不同回應，觀察 `setupBlockchain()` 是否被呼叫。最後一筆另以「卡住的 `setupBlockchain()`」模擬重建進行中，驗證重入防護 —— 重建整套 T-REX 的耗時遠超過 30 秒的排程間隔，下一次排程必然在前一次還沒結束時就進來。

| 測試情境 | 預期結果 | 實際結果 | 結果 |
|---|---|---|---|
| 節點不可達 | 排程直接跳過，不得觸發重建；且應在可達性檢查就返回，連 `ir_address` 都不該讀取 | 未呼叫 `setupBlockchain()`，`configRepo.findOne` 亦未被呼叫 | ✅ |
| **`getCode` 因網路異常拋錯** | **不得重建** —— RPC 瞬斷不等於合約消失 | 未呼叫 `setupBlockchain()` | ✅ |
| `getCode` 確實回傳 `0x`（合約真的不存在） | 才應觸發重建 | `setupBlockchain()` 被呼叫 1 次 | ✅ |
| 前一次重建尚未結束時，下一次排程進來 | 應被 `isRecovering` 擋下不重複部署；且重建結束後旗標要歸位，往後仍能再次自動修復 | 重建期間第二次呼叫未增加部署次數（維持 1 次）；釋放後再次呼叫成功觸發（累計 2 次） | ✅ |

> **突變驗證**：第 2 筆是全表最關鍵的一筆，因此另外做了反向確認 —— 將 `isConfigStale()` 例外分支的 `return false` 改回先前的 `return true` 後重跑，該筆立即失敗（`Expected number of calls: 0, Received number of calls: 1`），確認測試確實守得住這個行為而非恰好通過。驗證後已還原程式碼。第 4 筆尚未做同等的反向確認。

> **背景**：此分支原本為 `catch { return true }`，即「偵測不到就當作合約已消失」。配上自動重建等於一次網路抖動就可能觸發全面重部署，已於 commit `c5c8c6b` 改為保守的 `return false`。上表三筆即為此修正補上的迴歸防護。

### 8.4 鏈上／鏈下狀態一致性（五情境）

**測試檔案**：`src/blockchain/fault-injection-integrity.spec.ts`
**樣本**：12 個測試案例，通過率 12 / 12 = 100%

針對「服務重啟、重複事件、Nonce 衝突、區塊重組、通知失敗」五個指定情境進行故障注入。

> **本節測出三個缺口，其中兩個已修正**：
> · **通知失敗回滾已上鏈交易**（情境五）—— 已修正，見 (e)。
> · **Nonce 脫節後無法自行恢復**（情境三）—— 已修正，見 (c)。
> · **服務重啟重複執行鏈上轉帳**（情境一）—— **未修正**，屬架構層面改動（需改為兩階段提交），
> 現以測試釘住現況行為並標記為已知風險，見 (a)。

> **適用性先行說明（重要）**：五個情境中有兩項在本系統的架構下**沒有字面上的對應機制**，
> 若照字面撰寫等於測一個不存在的東西。經確認程式碼後改測最接近的等價風險，並在測試名稱中標明：
>
> · **重複事件**：全專案沒有任何鏈上事件訂閱（無 `contract.on` / WebSocket listener），
> 唯一消費 `Transfer` 事件的地方是 `reconcile()` 的 `queryFilter` 全量重建。
> 「同一事件被監聽兩次」不存在，等價風險為「對帳重複執行是否重複入帳」。
>
> · **區塊重組**：程式沒有任何 reorg 專門處理，所有 `.wait()` 皆為預設 1 個確認數。
> 等價風險為「已入帳的交易若在鏈上被 reorg 掉，是否偵測得到」，唯一安全網是 `reconcile()`。

#### (a) 情境一：服務重啟後的 pending 交易狀態

| 測試情境 | 預期結果 | 實際結果 | 結果 |
|---|---|---|---|
| 寫入途中程序被砍（commit 失敗） | 整筆 rollback、釋放連線，不得留下半完成狀態 | `rollbackTransaction` 與 `release` 各執行 1 次 | ✅ |
| 🔴 鏈上轉帳成功但 DB commit 失敗，重啟後重新結算 | （現況觀察）鏈上動作會被重跑 | 實測 `executeOnChainBuy` 被呼叫 2 次，使用者僅入帳 1 次 | ⚠️ 已知風險 |

**發現**：鏈上呼叫位於 DB commit **之前**（`transactions.service.ts` 的 `On-chain transfer (before DB commit)`），且重新結算前未檢查該筆是否已有 `tx_hash`。因此程序若在「鏈上已成功、DB 尚未 commit」的空窗被中斷，重啟後必然重跑鏈上轉帳，多付出的代幣無法自動追回。現況安全網僅有 `reconcile()`，屬事後偵測而非事前防止。**建議**：結算前先以 `tx_hash` 或獨立的「鏈上已送出」旗標做冪等檢查。

#### (b) 情境二：重複事件（等價風險 — 對帳重複執行）

| 測試情境 | 預期結果 | 實際結果 | 結果 |
|---|---|---|---|
| 連續執行兩次對帳 | 同一筆不一致不得被累計成兩筆 | 兩次的不一致筆數與檢查建案數完全相同 | ✅ |
| 鏈上轉帳已有對應交易紀錄 | 不得再判定為未追蹤轉帳（避免重複補建） | `UNTRACKED_TRANSFER` 為 0 筆 | ✅ |

**結論**：對帳為無狀態的全量比對，天生冪等，重跑不會重複入帳。

#### (c) 情境三：Nonce 衝突

| 測試情境 | 預期結果 | 實際結果 | 結果 |
|---|---|---|---|
| 鏈上轉帳遇 `NONCE_EXPIRED` | 錯誤如實往外拋，不得吞掉造成成功假象 | 正確拋出 | ✅ |
| nonce 脫節後的快取處理 | 應清除 `NonceManager` 快取，讓下一筆重新向節點取號 | `reset()` 被呼叫 1 次 | ✅ |
| 非 nonce 類的鏈上失敗（例：ERC-3643 合規擋下） | **不得**觸發 reset | `reset()` 未被呼叫 | ✅ |
| nonce 衝突後的資料庫狀態 | 標記 `CHAIN_FAILED`，且不得寫入假的 `tx_hash` | 狀態正確，`tx_hash` 維持未設定 | ✅ |

**已修正**：admin 錢包以 `ethers.NonceManager` 包裝，所有鏈上寫入共用同一把私鑰。先前程式中**沒有任何 `NonceManager.reset()` 的呼叫**，一旦送出失敗導致本地 nonce 計數與鏈上實際值脫節，後續每一筆都會沿用錯誤的 nonce 而連續失敗，直到服務重啟。

現已於 `executeOnChainBuy()` / `executeOnChainSell()` 的失敗路徑加入 `resetNonceIfDesynced()`。**刻意只在 `NONCE_EXPIRED` 與 `REPLACEMENT_UNDERPRICED` 兩種錯誤碼時才 reset** —— 其他失敗（例如合規檢查擋下轉帳）並不會讓 nonce 脫節，若一律 reset，反而可能在有其他交易在途時造成重號。上表第 3 筆即為此邊界撰寫。

#### (d) 情境四：區塊重組（等價風險 — 對帳能否偵測）

| 測試情境 | 預期結果 | 實際結果 | 結果 |
|---|---|---|---|
| 已入帳的轉帳在鏈上被 reorg 掉 | 對帳須偵測為餘額不一致 | 偵測到 `BALANCE_MISMATCH`，鏈上 0 / 資料庫 500 | ✅ |
| 偵測到不一致時的稽核紀錄 | 應寫入 `system_alerts` 而非靜默 | `logAlert` 確實被呼叫 | ✅ |

**觀察**：所有 `.wait()` 均為預設 1 個確認數，等同假設 1 個區塊即最終性。本專題在 Hardhat 本機網路上不會發生 reorg，但若上正式鏈需提高確認數。

#### (e) 情境五：成交通知寄送失敗

| 測試情境 | 預期結果 | 實際結果 | 結果 |
|---|---|---|---|
| 通知寫入失敗時的交易結果 | 交易須照常 commit，通知失敗只記錄告警 | `commitTransaction` 執行 1 次、未 rollback、鏈上轉帳保留 | ✅ |
| 通知的寫入時機與連線 | 須在 commit 之後、且不得再使用交易的 `queryRunner` | 交易範圍內查無通知寫入，改由獨立 repository 寫入 | ✅ |

**已修正**：先前成交通知使用與交易**相同的 `queryRunner`**（`qr.manager.save(UserNotification, ...)`）且位於 commit 之前，因此純通知層的故障會連帶讓一筆**已經上鏈**的交易被回滾 —— 代幣在使用者鏈上錢包裡，平台帳上卻沒有這筆交易。

現已將通知寫入移到 `commitTransaction()` 之後，改以獨立的 `notifRepo` 寫入並自帶 try/catch，失敗僅記錄 ERROR。通知屬於可補送的周邊功能，不應具備否決已完成鏈上轉帳的能力。代價是通知本身在極端情況下可能遺失，但相較於回滾一筆已上鏈的交易，這是明確較小的損失。
